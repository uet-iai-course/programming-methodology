1.
Bản chất của
Mẫu thiết kế

Định nghĩa Pattern

Pattern = Giải pháp cho một Vấn đề trong một Ngữ cảnh.
  • Context: Tình huống lặp đi lặp lại.
  • Problem: Mục tiêu + ràng buộc.
  • Solution: Bản thiết kế giải quyết vấn đề.

"Forces" - Lực tác động

Trong Pattern, "Problem" = Forces (Lực):

☀️ Goals (Mục tiêu)

Điều bạn muốn đạt được.

🌑 Constraints (Ràng buộc)

Giới hạn về thời gian, tiền bạc, hiệu năng...

⚖️ Pattern hữu ích khi CÂN BẰNG được cả hai Lực.

Ví dụ: Đây có phải Pattern?

  • Ngữ cảnh: Bị khóa chìa trong xe, phải đi làm đúng giờ.
  • Vấn đề: Đúng giờ + ít tốn tiền.
  • Giải pháp: Đập vỡ kính xe, lấy chìa, lái đi làm.
❌ KHÔNG phải Pattern vì:
  • Vi phạm ràng buộc "ít tốn tiền" → chưa cân bằng lực.
  • Không lặp lại được trong thực tế.

Tại sao phải học Patterns?

🗣️ Shared Vocabulary: Nói "Dùng Observer" thay vì giải thích 15 phút.
♻️ Tái sử dụng kinh nghiệm: Kế thừa chất xám của các lập trình viên giỏi nhất.
🛡️ Tránh bẫy: Không lặp lại sai lầm thiết kế phổ biến.

Quy tắc số 3 (Rule of Three)

Nguyên tắc vàng
Pattern được khám phá, không phải phát minh.
  • Chỉ là Pattern khi đã thành công trong ít nhất 3 hệ thống thực tế.
  • Pattern là hướng dẫn, không phải luật cứng nhắc.

2.
Thế giới Patterns
& Phân loại

Catalog: Cấu trúc 1 Pattern

Mọi pattern chuẩn đều theo template (Catalog):

  • Name: Tên gọi.
  • Intent: Mục đích.
  • Motivation: Ví dụ minh họa.
  • Applicability: Khi nào dùng.
  • Structure: Sơ đồ UML.
  • Participants: Các Class tham gia.
  • Consequences: Ưu/Nhược điểm.
  • Sample Code: Mã mẫu.

Sách GoF (1995)

  • Design Patterns: Elements of Reusable Object-Oriented Software.
  • 4 tác giả: Gang of Four (GoF).
  • Phân loại 23 patterns căn bản.

Phân loại 23 Mẫu GoF

Nhóm Mục tiêu Số lượng
Creational Tách biệt logic tạo đối tượng. 5 mẫu
Structural Lắp ráp đối tượng thành cấu trúc lớn. 7 mẫu
Behavioral Quản lý giao tiếp và phân quyền. 11 mẫu

Phạm vi (Scope) của Pattern

Class Scope
  • Dùng Kế thừa (Inheritance).
  • Tĩnh — cố định lúc Compile-time.
Object Scope
  • Dùng Thành phần (Composition).
  • Động — linh hoạt đổi lúc Runtime.

* Hầu hết GoF Patterns dùng Object Scope.

Patterns Zoo (Vườn thú Pattern)

Pattern có ở mọi lĩnh vực, không chỉ OOP:

  • 🏛️ Architectural: Xây dựng, đô thị.
  • 💻 Application: Kiến trúc hệ thống (MVC).
  • ⚙️ Domain-Specific: Nhúng, J2EE.
  • 💼 Business: Quy trình kinh doanh.
  • 👥 Organizational: Team (Agile).
  • 🎨 UI Design: Nút bấm, Menu.

3.
Creational Patterns
(Nhóm Khởi tạo)

Bản chất Creational

Tách biệt quá trình tạo đối tượng ra khỏi hệ thống sử dụng nó.
  • Giấu logic dùng toán tử new.
  • Hệ thống độc lập với cách object được tạo ra.
  • 5 mẫu: Singleton, Factory Method, Abstract Factory, Builder, Prototype.

1. Singleton Pattern

Intent: Đảm bảo 1 Class chỉ có 1 Instance duy nhất với điểm truy cập toàn cục.
  • Dùng cho: DB Connection, Log File, Cache.
  • Nhược điểm: Giống biến toàn cục — khó viết Unit Test.

Code ví dụ: Singleton

Bí quyết: constructor là private → chặn dùng new từ bên ngoài.


public class DatabaseConnection {
    // 1. Biến static lưu instance duy nhất
    private static DatabaseConnection instance;

    // 2. Private constructor
    private DatabaseConnection() {
        System.out.println("Kết nối tới Database...");
    }

    // 3. Điểm truy cập toàn cục (Lazy Initialization)
    public static DatabaseConnection getInstance() {
        if (instance == null) {
            instance = new DatabaseConnection();
        }
        return instance;
    }
}

// Client:
DatabaseConnection db1 = DatabaseConnection.getInstance();
DatabaseConnection db2 = DatabaseConnection.getInstance(); // Cùng vùng nhớ

2. Factory Method & Abstract Factory

Factory Method:
Lớp con tự quyết định đối tượng cụ thể được tạo ra.

(Tạo 1 loại sản phẩm)
Abstract Factory:
Tạo cả họ (family) đối tượng liên quan.

(VD: WinFactory → WinButton, WinMenu)
📖 Từ Phụ lục sách

3. Builder Pattern

Intent: Xây dựng sản phẩm phức tạp theo từng bước (in steps).
  • Kịch bản: Lịch trình nghỉ dưỡng (Vacation Planner).
  • Mỗi ngày là 1 bước: Đặt KS → Vé công viên → Ăn tối.
  • Kết quả là cấu trúc cây (Composite) phức tạp.

Code ví dụ: Builder

Fluent Interface — đọc như ngôn ngữ tự nhiên.


// Tạo Pizza mà không cần truyền 10 tham số vào Constructor
Pizza myPizza = new Pizza.Builder("Large") // Bắt buộc
                    .addCheese()           // Tùy chọn
                    .addPepperoni()
                    .addBacon()
                    .build();              // Tạo thành phẩm

System.out.println(myPizza.getDescription());
Lợi ích: Giải quyết lỗi "Telescoping Constructor" — constructor quá nhiều tham số.

Sơ đồ Builder

4. Prototype Pattern

Intent: Tạo đối tượng mới bằng cách sao chép (clone) từ nguyên mẫu có sẵn.
  • Dùng khi khởi tạo bằng new quá chậm hoặc tốn kém.
  • Kịch bản: Game sinh ra hàng ngàn quái vật.
  • Thay vì new Monster(...) → dùng registry.get("orc").clone().

Sơ đồ Prototype

4.
Structural Patterns
(Nhóm Cấu trúc)

Bản chất Structural

Cách lắp ráp các đối tượng thành cấu trúc lớn hơn.
  • Giữ được tính linh hoạt và hiệu quả.
  • 7 mẫu: Adapter, Facade, Decorator, Proxy, Composite, Bridge, Flyweight.

1. Nhóm bọc đối tượng (Wrappers)

Pattern Mục đích
Adapter Đổi interface này → interface khác. (Bộ chuyển điện)
Decorator Gắn thêm hành vi, không đổi interface. (Topping trà sữa)
Facade Interface đơn giản che hệ thống phức tạp. (Nút bật rạp phim)
Proxy Kiểm soát quyền truy cập vào đối tượng gốc. (Bảo vệ canh cổng)

Code ví dụ: Adapter

Tương thích hệ thống MỚI với hệ thống CŨ (Legacy).


// 1. Hệ thống cũ trả về XML
class OldLibrary {
    public String getXMLData() { return "100"; }
}

// 2. Hệ thống mới chỉ nhận JSON
interface NewInterface {
    String getJSONData();
}

// 3. Adapter: cắm "2 chấu" vào "3 chấu"
class XmlToJsonAdapter implements NewInterface {
    private OldLibrary oldLib = new OldLibrary();

    @Override
    public String getJSONData() {
        String xml = oldLib.getXMLData();
        return convertXmlToJson(xml);
    }
}

Code ví dụ: Decorator

Gắn thêm hành vi (bọc vỏ) mà không dùng Kế thừa.


// 1. Đối tượng lõi
Beverage myDrink = new Espresso();
System.out.println(myDrink.cost()); // 20k

// 2. Bọc thêm "Sữa"
myDrink = new MilkDecorator(myDrink);
System.out.println(myDrink.cost()); // 25k

// 3. Bọc thêm "Trân châu"
myDrink = new BobaDecorator(myDrink);
System.out.println(myDrink.cost()); // 30k

// Lõi bên trong không biết nó đang bị bọc!

2. Composite Pattern

Intent: Xử lý đối tượng đơn lẻ và tập hợp như nhau (cấu trúc cây).
  • Ví dụ: File và Folder.
  • getSize() trên File → dung lượng file.
  • getSize() trên Folder → cộng dồn tất cả file bên trong.
📖 Từ Phụ lục sách

3. Bridge Pattern

Intent: Tách Abstraction và Implementation để hai bên phát triển độc lập.
  • Kịch bản: Remote (Basic/Advanced) × TV (Sony/RCA).
  • Kế thừa → bùng nổ class: SonyAdvancedRemote, ...
  • Giải pháp: Remote Has-A TV (Composition).

Sơ đồ Bridge

📖 Từ Phụ lục sách

4. Flyweight Pattern

Intent: Dùng 1 instance đại diện cho hàng vạn "thực thể ảo" — tiết kiệm RAM.
  • Kịch bản: Vẽ 1.000 cái cây.
  • Intrinsic state (chung): hình dáng, lá → 1 object Tree duy nhất.
  • Extrinsic state (riêng): tọa độ X, Y → mảng bên ngoài quản lý.

Sơ đồ Flyweight

5.
Behavioral Patterns
(Nhóm Hành vi)

Bản chất Behavioral

Tập trung vào phân chia trách nhiệm và giao tiếp giữa các object.
  • Xử lý sự phức tạp của luồng điều khiển (control flow).
  • 11 mẫu: Observer, Strategy, State, Command, Iterator, Template Method...

1. Observer Pattern

Quan hệ 1-Nhiều. Subject đổi trạng thái → tự động thông báo cho tất cả Observers.
  • Ví dụ: Kênh YouTube và người đăng ký.
  • Dùng trong: Hệ thống UI Event, pub/sub messaging.

Code ví dụ: Observer

Mô hình Subscribe / Publish (Đăng ký - Lắng nghe).


class YoutubeChannel {
    private List subs = new ArrayList<>();

    public void subscribe(Subscriber s) { subs.add(s); }

    // Upload video → TỰ ĐỘNG thông báo cho mọi người
    public void uploadVideo(String title) {
        for (Subscriber s : subs) {
            s.update(title);
        }
    }
}

// Client:
channel.subscribe(userA);
channel.subscribe(userB);

channel.uploadVideo("Review iPhone 15");
// User A và B nhận thông báo ngay lập tức!

2. Strategy & State

Strategy:
Đóng gói thuật toán, đổi lúc runtime.

VD: Đổi cổng thanh toán, đổi cách sắp xếp.
State:
Hành vi thay đổi theo state nội bộ. Xóa bỏ if/else khổng lồ.

VD: Máy bán nước tự động.

Code ví dụ: Strategy

Đóng gói thuật toán — đổi chiến lược dễ dàng, thay thế if/else dài.


// 1. Interface chung cho thuật toán thanh toán
interface PaymentStrategy {
    void pay(int amount);
}

class MomoPayment implements PaymentStrategy { ... }
class VisaPayment implements PaymentStrategy { ... }

// 2. Context: Giỏ hàng
class ShoppingCart {
    private PaymentStrategy strategy;

    public void setStrategy(PaymentStrategy strategy) {
        this.strategy = strategy;
    }

    public void checkout(int amount) {
        strategy.pay(amount); // Chạy thuật toán đã lắp
    }
}

3. Command Pattern

Đóng gói Yêu cầu (Request) thành một đối tượng.
  • Hỗ trợ Undo/Redo, xếp job vào Queue.
  • Ví dụ: Viết giấy Order trong quán ăn.
📖 Từ Phụ lục sách

4. Chain of Responsibility

Intent: Móc xích các Handler, cho nhiều đối tượng cơ hội xử lý Request.
  • Kịch bản: Phân loại Email.
  • SpamHandler → FanHandler → ComplaintHandler
  • Ai xử lý được thì dừng; nếu không thì đẩy tiếp.

Sơ đồ Chain of Responsibility

5. Interpreter Pattern

Intent: Xây dựng "Người phiên dịch" cho một ngôn ngữ đơn giản dựa trên Ngữ pháp (Grammar).
  • Kịch bản: Ngôn ngữ điều khiển Vịt (Duck Pond Simulator).
  • Mỗi rule ngữ pháp = 1 Class.
  • Nhược điểm: Số class bùng nổ nếu ngôn ngữ phức tạp.

Sơ đồ Interpreter

📖 Từ Phụ lục sách

6. Mediator Pattern

Intent: Gom các giao tiếp phức tạp vào 1 class trung gian (Mediator).
  • Kịch bản: Nhà thông minh (Smart Home).
  • Báo thức, Lịch, Máy pha Cafe → không giao tiếp chéo.
  • Tất cả báo cáo cho Mediator; Mediator chứa logic điều phối.

7. Memento Pattern

Intent: Khôi phục State trước đó (Undo) mà không vi phạm Encapsulation.
  • Kịch bản: Tính năng Save Game.
  • Object tạo hộp kín Memento → Client giữ nhưng không đọc/sửa được.

Sơ đồ Memento

8. Visitor Pattern

Intent: Thêm tính năng mới vào cấu trúc Object mà không sửa code class gốc.
  • Kịch bản: Thêm chức năng đếm Calories cho Menu.
  • Visitor đi qua cây Composite của Menu để thu thập dữ liệu.
  • Nhược điểm: Phá vỡ Encapsulation của Object.

6.
Tư duy Patterns
& Anti-Patterns

Nguyên tắc K.I.S.S

K.I.S.S — Keep It Simple, Stupid
  • Đừng dùng Pattern chỉ để "trông có vẻ nguy hiểm".
  • Code đơn giản = code tốt.
  • Developer giỏi viết code ai cũng hiểu.

Khi nào NÊN & KHÔNG NÊN dùng?

✅ NÊN dùng khi:
  • Giải pháp thô không đáp ứng được.
  • Điểm mở rộng đã rõ ràng.
  • Đang Refactoring code smell.
❌ KHÔNG nên khi:
  • Thay đổi chỉ là "giả định". (YAGNI)
  • Sinh ra quá nhiều class/interface rác.
  • Giải pháp đơn giản vẫn hoạt động tốt.

Anti-Patterns là gì?

Pattern = giải pháp TỐT. Anti-pattern = giải pháp TỒI TỆ trông hấp dẫn ban đầu.

Ví dụ: Golden Hammer (Cây búa vàng)
  • "Tôi giỏi Java → dùng Java làm mọi thứ, kể cả script đơn giản."
  • "Có búa trong tay thì nhìn đâu cũng thấy đinh."

3 Cấp độ tư duy

🔴 Beginner: Dùng pattern mọi nơi — "Càng nhiều càng vip."
🟡 Intermediate: Biết chọn lọc, nhưng vẫn ép code theo pattern.
🟢 Zen Mind: Tư duy từ nguyên lý SOLID. Pattern xuất hiện tự nhiên.

6 điều cần nhớ

1. Không phải thuốc tiên: Cân nhắc lợi hại.
2. Từ vựng chung: Lợi ích lớn nhất.
3. Creational: Tạo Object (Builder, Prototype).
4. Structural: Lắp ráp (Bridge, Flyweight).
5. Behavioral: Giao tiếp (Mediator, Visitor...).
6. Refactoring: Lúc lý tưởng nhất để dùng.
