1.
Pattern là gì?

Khi code bắt đầu gây khó

  • new SomeClass() rải khắp nơi — đổi class phải sửa hàng chục chỗ.
  • if/else if cứ dài thêm mỗi lần thêm loại mới.
  • Kế thừa chồng chéo — số lớp tăng theo cấp số nhân.

Những vấn đề này đã có lời giải quen thuộc — đó là pattern.

Mẫu thiết kế là gì?

Pattern = giải pháp cho một vấn đề trong một ngữ cảnh.
  • Ngữ cảnh: tình huống lặp lại.
  • Vấn đề: mục tiêu và ràng buộc.
  • Giải pháp: lời giải tổng quát.

Mục tiêu và ràng buộc (Forces)

Mỗi bài toán có nhiều yêu cầu kéo theo đánh đổi:

  • Mục tiêu: linh hoạt, tái sử dụng, dễ mở rộng.
  • Ràng buộc: thời gian, chi phí, hiệu năng, độ phức tạp.

Pattern tốt giúp cân bằng các yêu cầu đó, thay vì tối ưu một mặt rồi làm hỏng mặt khác.

Nhận diện pattern

  • Ngữ cảnh: Mỗi lần thêm loại thanh toán mới, lại sửa một chuỗi if/else dài trong OrderProcessor.
  • Vấn đề: Code chạy được, nhưng mỗi lần thêm là một lần rủi ro.
  • Giải pháp tạm: Thêm một nhánh else if nữa vào.

Kết luận: Không phải pattern — đây là mẹo tạm, không tổng quát và càng dùng càng khó bảo trì.

Vì sao phải học pattern?

  • Từ vựng chung: Nói “Observer” là cả nhóm hiểu.
  • Tái sử dụng: Không phải nghĩ lại từ đầu.
  • Tránh bẫy: Bớt lặp lại sai lầm cũ.

Quy tắc số 3

Một lời giải thường chỉ được nhìn nhận là pattern sau khi xuất hiện ở ít nhất 3 hệ thống khác nhau — không phải ngẫu nhiên, mà thực sự giải quyết cùng một vấn đề.
  • Pattern được khám phá, không phải phát minh.
  • Con số 3 chỉ là một quy tắc kinh nghiệm.

2.
Phân loại pattern

Cấu trúc một pattern

Một pattern thường được mô tả qua các phần sau:

  • Tên gọi
  • Mục đích
  • Ngữ cảnh sử dụng
  • Cấu trúc
  • Thành phần
  • Hệ quả
  • Mã mẫu

Sách GoF (1995)

  • Design Patterns: Elements of Reusable Object-Oriented Software.
  • 4 tác giả: Gang of Four (GoF).
  • Giới thiệu và phân loại 23 mẫu thiết kế kinh điển.

Phần lớn GoF pattern thuộc mức đối tượng.

Pattern ngoài OOP

Pattern có ở nhiều lĩnh vực:

  • Kiến trúc: xây dựng, đô thị.
  • Ứng dụng: kiến trúc hệ thống như MVC.
  • Theo miền: hệ nhúng, J2EE.
  • Kinh doanh: quy trình nghiệp vụ.
  • Tổ chức: cách vận hành nhóm.
  • UI: nút bấm, menu, điều hướng.

Ngoài SOLID, nguyên tắc "ưu tiên composition hơn inheritance" (GoF) cũng hiện rõ ở Decorator, Bridge, Composite, Flyweight.

3.
Nhóm khởi tạo

Bản chất nhóm khởi tạo

Tách biệt quá trình tạo đối tượng ra khỏi hệ thống sử dụng nó.
  • Client không cần biết cụ thể lớp nào được tạo ra.
  • Code không phụ thuộc cách tạo đối tượng.
  • 5 mẫu: Singleton, Factory Method, Abstract Factory, Builder, Prototype.

Singleton: chỉ một instance dùng chung

  • Ý chính: Chỉ có một instance.
  • Hay gặp: logger, cache, cấu hình dùng chung.
  • Lưu ý: Gần với biến toàn cục, khó test. Trong code hiện đại, thường thay bằng Dependency Injection — truyền đối tượng dùng chung qua constructor.

Mã ví dụ: Singleton

constructor để private: chặn việc tạo trực tiếp từ bên ngoài.


class DatabaseConnection {
private:
    DatabaseConnection() {
        std::cout << "Kết nối tới Database...\n";
    }
public:
    DatabaseConnection(const DatabaseConnection&) = delete;
    DatabaseConnection& operator=(const DatabaseConnection&) = delete;

    static DatabaseConnection& getInstance() {
        static DatabaseConnection instance;
        return instance;
    }
};
// Client:
auto& db1 = DatabaseConnection::getInstance();
auto& db2 = DatabaseConnection::getInstance(); // Cùng đối tượng

Ai quyết định? Lớp con override phương thức Factory object riêng
Ví dụ Chi nhánh HN pha phin,
chi nhánh SG pha sữa đá		 Nội thất Modern → ghế + bàn Modern

Mã ví dụ: Factory Method

Lớp con quyết định pha loại cà phê nào — client chỉ gọi serve().


class CoffeeShop {
public:
    virtual Coffee* brew() = 0;   // factory method
    void serve() {
        Coffee* c = brew();
        c->prepare();
        c->pour();
    }
    virtual ~CoffeeShop() = default;
};
class HanoiShop : public CoffeeShop {
public:
    Coffee* brew() override { return new CaPhePhin(); }
};
class SaigonShop : public CoffeeShop {
public:
    Coffee* brew() override { return new CaPheSuaDa(); }
};
// Client: shop->serve() — không cần biết pha kiểu gì

Mã ví dụ: Abstract Factory

Factory tạo cả bộ — ghế và bàn luôn cùng phong cách.


class FurnitureFactory {
public:
    virtual Chair* createChair() = 0;
    virtual Table* createTable() = 0;
    virtual ~FurnitureFactory() = default;
};

class ModernFactory : public FurnitureFactory {
public:
    Chair* createChair() override { return new ModernChair(); }
    Table* createTable() override { return new ModernTable(); }
};

class ClassicFactory : public FurnitureFactory {
public:
    Chair* createChair() override { return new ClassicChair(); }
    Table* createTable() override { return new ClassicTable(); }
};
// Client dùng FurnitureFactory* — bộ sản phẩm luôn tương thích

Builder: xây đối tượng phức tạp theo từng bước

  • Ý chính: Xây sản phẩm phức tạp theo từng bước.
  • Hay gặp: sản phẩm có nhiều phần tùy chọn.
  • Ví dụ: tạo pizza với nhiều lựa chọn topping.
  • Lưu ý: Cùng quy trình xây dựng, tạo ra sản phẩm khác nhau tuỳ cấu hình.

Mã ví dụ: Builder

Fluent interface: gọi nối tiếp theo từng bước.


// Tạo Pizza mà không cần truyền 10 tham số vào Constructor
Pizza myPizza = Pizza::Builder("Large") // Bắt buộc
                    .addCheese()        // Tùy chọn
                    .addPepperoni()
                    .addBacon()
                    .build();           // Tạo thành phẩm

std::cout << myPizza.getDescription() << '\n';

Lợi ích: tránh constructor quá dài.

Ví dụ: Một Sơ đồ Builder

Prototype: tạo đối tượng mới bằng cách sao chép

  • Ý chính: Tạo đối tượng mới bằng cách sao chép đối tượng có sẵn.
  • Hay gặp: việc khởi tạo tốn kém; cần nhiều đối tượng giống nhau.
  • Ví dụ: Game sinh nhanh quái vật: registry.get("orc").clone().

Ví dụ: Một Sơ đồ Prototype

Client gọi clone() thay vì new — không cần biết lớp cụ thể.

4.
Nhóm cấu trúc

Bản chất nhóm cấu trúc

Cách lắp ráp các đối tượng thành cấu trúc lớn hơn.
  • Giữ được tính linh hoạt.
  • 7 mẫu: Adapter, Facade, Decorator, Proxy, Composite, Bridge, Flyweight.

Các pattern bọc đối tượng

Pattern Mục đích
Adapter Đổi interface. (Bộ chuyển điện)
Decorator Gắn thêm hành vi. (Topping trà sữa)
Facade Che hệ thống phức tạp. (Nút bật rạp phim)
Proxy Kiểm soát truy cập. (Bảo vệ canh cổng)

Adapter: chuyển đổi interface

  • Ý chính: Bọc một đối tượng có interface không tương thích, biến nó thành interface mà client cần.
  • Hay gặp: tích hợp thư viện cũ, API bên thứ ba, hệ thống legacy.
  • Ví dụ: Ổ cắm 2 chấu cắm vào ổ 3 chấu — cần bộ chuyển.
  • Cấu trúc: Adapter kế thừa interface mới, bên trong giữ đối tượng cũ và dịch lời gọi.

Mã ví dụ: Adapter

Hệ thống mới cần JSON, thư viện cũ chỉ có XML — Adapter dịch giữa hai bên.


// 1. Hệ thống cũ trả về XML
class OldLibrary {
public:
    std::string getXmlData() const { return "100"; }
};
// 2. Hệ thống mới chỉ nhận JSON
class NewInterface {
public:
    virtual std::string getJsonData() const = 0;
    virtual ~NewInterface() = default;
};
// 3. Adapter: cắm "2 chấu" vào "3 chấu"
class XmlToJsonAdapter : public NewInterface {
private:
    OldLibrary oldLib;
public:
    std::string getJsonData() const override {
        std::string xml = oldLib.getXmlData();
        return convertXmlToJson(xml);
    }
};

Decorator: thêm hành vi mà không sửa lớp gốc

  • Ý chính: Bọc đối tượng bằng một lớp cùng interface — thêm hành vi mà không sửa lớp gốc, không tạo lớp con.
  • Hay gặp: cần kết hợp nhiều tính năng tùy chọn linh hoạt.
  • Ví dụ: Ly cà phê + sữa + trân châu — mỗi topping là một lớp bọc, cộng dồn giá.
  • Khác Adapter: Adapter đổi interface, Decorator giữ nguyên interface.

Mã ví dụ: Decorator (client)

Bọc lớp này lên lớp kia — mỗi lớp bọc thêm hành vi.


// Lõi: chỉ là Espresso thuần
auto myDrink = make_shared<Espresso>();
cout << myDrink->cost() << "k\n"; // 20k

// Bọc thêm Sữa
myDrink = make_shared<MilkDecorator>(myDrink);
cout << myDrink->cost() << "k\n"; // 25k

// Bọc thêm Trân châu
myDrink = make_shared<BobaDecorator>(myDrink);
cout << myDrink->cost() << "k\n"; // 30k
// Lõi Espresso không thay đổi; cost() được cộng dồn từ ngoài vào

Cấu trúc lớp Decorator

Decorator kế thừa cùng interface với đối tượng gốc, đồng thời giữ tham chiếu tới nó.


class Beverage {
public:
    virtual int cost() const = 0;
    virtual ~Beverage() = default;
};
class Espresso : public Beverage {
public:
    int cost() const override { return 20; }
};
// Decorator giữ tham chiếu tới Beverage bên trong
class BeverageDecorator : public Beverage {
protected:
    shared_ptr<Beverage> inner;
public:
    BeverageDecorator(shared_ptr<Beverage> b) : inner(b) {}
};
class MilkDecorator : public BeverageDecorator {
public:
    using BeverageDecorator::BeverageDecorator;
    int cost() const override { return inner->cost() + 5; }
};

Composite: phần tử đơn hay nhóm — cùng một giao diện

  • Ý chính: Xử lý đối tượng đơn lẻ và tập hợp giống nhau.
  • Hay gặp: cần thao tác giống nhau trên phần tử đơn và cả nhóm phần tử.
  • Ví dụ: File và Folder.
  • Lưu ý: getSize() trên file trả về dung lượng file, còn trên folder trả về tổng dung lượng bên trong.

Bridge: khi có hai chiều thay đổi độc lập

  • Ý chính: Khi có 2 trục thay đổi độc lập, dùng composition thay kế thừa.
  • Hay gặp: mỗi trục (abstraction và implementation) cần thay đổi riêng mà không ảnh hưởng nhau.
  • Ví dụ: Remote (Basic/Advanced) × TV (Sony/RCA).
  • Lưu ý: Kế thừa trực tiếp dễ làm số lớp tăng rất nhanh.
  • Giải pháp: Remote chứa TV.

Sơ đồ Bridge

Abstraction và Implementation thay đổi độc lập — nối nhau qua composition.

Flyweight: dùng chung dữ liệu bất biến

  • Ý chính: Dùng chung dữ liệu bất biến cho nhiều đối tượng.
  • Hay gặp: số lượng đối tượng rất lớn, phần lớn dữ liệu giống nhau.
  • Ví dụ: Vẽ 1.000 cây — dùng chung hình dáng/màu lá, chỉ khác tọa độ X, Y.

5.
Nhóm hành vi

Bản chất nhóm hành vi

Tập trung vào phân chia trách nhiệm và giao tiếp giữa các đối tượng.
  • Xử lý luồng điều khiển giữa các đối tượng.
  • 11 mẫu: Observer, Strategy, State, Command, Iterator, Template Method...
  • Trong bài này: đi sâu 3 mẫu tiêu biểu, còn lại nhận mặt.

Observer: một đổi, nhiều nơi được báo

  • Ý chính: Một đổi, nhiều nơi được báo.
  • Ví dụ: Kênh YouTube và người đăng ký.
  • Hay gặp: UI event, pub/sub, dữ liệu thay đổi cần báo nhiều nơi.

Mã ví dụ: Observer

Subject giữ danh sách Observer; khi thay đổi, tự động thông báo tất cả.


class YoutubeChannel {           // Subject
private:
    std::vector<Subscriber*> subs;
public:
    void subscribe(Subscriber* s) { subs.push_back(s); }

    void uploadVideo(const std::string& title) {
        for (Subscriber* s : subs)
            s->update(title);    // Thông báo tất cả Observer
    }
};

// Client:
YoutubeChannel channel;
UserA userA;  UserB userB;

channel.subscribe(&userA);
channel.subscribe(&userB);
channel.uploadVideo("Review iPhone 15");
// → userA.update() và userB.update() đều được gọi

Strategy: đổi thuật toán mà không sửa code gọi

  • Ý chính: Đóng gói mỗi thuật toán thành một lớp riêng — client chọn và thay lúc chạy.
  • Hay gặp: nhiều cách xử lý cùng một việc (thanh toán, sắp xếp, nén file...).
  • Ví dụ: Giỏ hàng chấp nhận Momo, Visa, COD — mỗi cổng thanh toán là một strategy.

Strategy và OCP (bài 6)

Nhớ bài 6: DiscountCalculator dùng if/else cho mỗi loại giảm giá — thêm loại mới phải sửa code cũ.

  • Giải pháp bài 6: tách IDiscount, mỗi loại giảm giá là một lớp.
  • Đó chính là Strategy — mỗi lớp IDiscount là một strategy.
  • Thêm loại mới = thêm lớp mới, không đụng code cũ → OCP.
  • Client phụ thuộc vào interface, không phụ thuộc implementation → DIP.

Strategy vs State: ai quyết định hành vi?

Strategy State
Client chọn thuật toán từ bên ngoài. Hành vi tự đổi theo trạng thái bên trong.
cart.setStrategy(new MomoPayment()) NoMoneyState → HasMoneyState → SoldOutState

Chốt: Strategy — client quyết định; State — đối tượng tự quyết định.

Mã ví dụ: Strategy

Đóng gói thuật toán để thay chiến lược dễ dàng.


// 1. Interface chung cho thuật toán thanh toán
class PaymentStrategy {
public:
    virtual void pay(int amount) = 0;
    virtual ~PaymentStrategy() = default;
};

class MomoPayment : public PaymentStrategy { ... };
class VisaPayment : public PaymentStrategy { ... };

// 2. Context: Giỏ hàng
class ShoppingCart {
private:
    PaymentStrategy* strategy = nullptr;

public:
    void setStrategy(PaymentStrategy* s) {
        strategy = s;
    }

    void checkout(int amount) {
        strategy->pay(amount); // Chạy thuật toán đã lắp
    }
};

Command: đóng gói yêu cầu thành đối tượng

  • Ý chính: Đóng gói yêu cầu thành một đối tượng.
  • Hay gặp: cần xếp hàng, ghi log, hoặc hỗ trợ undo/redo.
  • Ví dụ: Giấy order trong quán ăn.

Mã ví dụ: Command

Đóng gói yêu cầu thành đối tượng — cho phép undo/redo.


// 1. Interface lệnh
class Command {
public:
    virtual void execute() = 0;
    virtual void undo() = 0;
    virtual ~Command() = default;
};

// 2. Lệnh cụ thể: bật đèn
class TurnOnLightCommand : public Command {
    Light& light;
public:
    TurnOnLightCommand(Light& l) : light(l) {}
    void execute() override { light.turnOn(); }
    void undo()    override { light.turnOff(); }
};

// 3. Invoker: remote điều khiển
class RemoteControl {
    std::stack<Command*> history;
public:
    void pressButton(Command* cmd) {
        cmd->execute();
        history.push(cmd);   // Lưu để undo
    }
    void pressUndo() {
        if (!history.empty()) {
            history.top()->undo();
            history.pop();
        }
    }
};

Chain of Responsibility: chuyền yêu cầu qua chuỗi xử lý

  • Ý chính: Nối các handler thành chuỗi; xử lý được thì dừng, không thì chuyển tiếp.
  • Ví dụ: Phân loại email — SpamHandler → FanHandler → ComplaintHandler.
  • Hay gặp: nhiều bộ xử lý độc lập, không biết trước cái nào sẽ xử lý.

Sơ đồ Chain of Responsibility

Mỗi handler xử lý hoặc chuyển tiếp — client không cần biết ai xử lý.

Khi nào nên dùng pattern?

Nguyên tắc K.I.S.S

K.I.S.S (Keep It Simple, Stupid): giữ thiết kế đơn giản.

  • Đừng dùng pattern chỉ để làm thiết kế trông phức tạp hơn.
  • Code đơn giản thường là code tốt.
  • Code tốt là code người khác còn đọc được.

Bộ câu hỏi tự kiểm trước khi dùng pattern

  1. Vấn đề này đã lặp lại đủ rõ chưa, hay vẫn còn mơ hồ?
  2. Điểm thay đổi trong tương lai nằm ở đâu — đã xác định được chưa?
  3. Tách theo tạo đối tượng, cấu trúc, hay hành vi?
  4. Cách đơn giản nhất hiện tại còn đủ dùng không?

Nếu câu 4 trả lời "còn đủ dùng" — chưa cần pattern.

Khi nào nên dùng pattern?

Nên dùng khi Chưa nên khi
Giải pháp đơn giản không đủ. Vấn đề vẫn chưa lặp lại đủ rõ.
Điểm mở rộng đã rõ. Dễ sinh quá nhiều lớp.
Đang tái cấu trúc code smell (dấu hiệu thiết kế có vấn đề). Giải pháp đơn giản vẫn chạy tốt.

Anti-pattern là gì?

Anti-pattern là lời giải tưởng hay nhưng dẫn đến thiết kế tồi.

  • Golden Hammer — có búa trong tay thì nhìn đâu cũng thấy đinh. Giỏi một công cụ không có nghĩa là dùng nó cho mọi bài toán.
  • God Object — một lớp biết và làm tất cả mọi thứ. Vi phạm SRP, khó test, khó bảo trì.

Ba mức tư duy

  1. Mức 1: Thấy đâu cũng muốn gắn pattern. — "Cần lưu config, dùng Singleton thôi!"
  2. Mức 2: Biết chọn, nhưng đôi khi còn ép mẫu. — Dùng Observer dù chỉ có một subscriber.
  3. Mức 3: Bắt đầu từ vấn đề và nguyên lý, rồi mới chọn pattern. — Pattern xuất hiện tự nhiên từ thiết kế.

Tổng kết

Nhìn pattern như những lời giải quen thuộc.

Nhìn lại bài học

  1. Pattern = lời giải quen thuộc cho vấn đề lặp lại — được khám phá, không phải phát minh.
  2. SOLID là nguyên lý; pattern là cách triển khai — Strategy/Decorator hỗ trợ OCP, Command/Strategy hỗ trợ DIP.
  3. Ba nhóm: khởi tạo (ai tạo), cấu trúc (ghép thế nào), hành vi (giao tiếp ra sao).
  4. Dùng có chọn lọc: đơn giản trước — pattern xuất hiện tự nhiên khi tái cấu trúc, không phải ép từ đầu.
  5. Lợi ích lớn nhất: từ vựng chung — nói "Observer" cả nhóm hiểu ngay.
